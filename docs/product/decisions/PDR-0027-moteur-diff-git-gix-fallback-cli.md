# PDR-0027 - Moteur de diff Git v2.4 : gix en backend primaire + fallback git CLI cohérent

**Status: validated**

Introduit les dépendances structurantes de la **stack Git v2.4** dans `crates/nyx-core` (sidecar-side, PDR-0007) : `gix` (`0.85.0`, `default-features = false` + features `sha1`, `blob-diff`, `revision`, `dirwalk`, `status`, `max-performance-safe`) comme moteur Git primaire du diff/review v2.4 (`crates/nyx-core/src/git_diff.rs`, `crates/nyx-core/src/git_views.rs`, un `git` CLI restant comme fallback cohérent) ; et `notify` (`7`, default features) comme **source d'événements filesystem OS-native** (inotify / FSEvents / ReadDirectoryChangesW) qui alimente le rafraîchissement temps réel **sans polling** des vues dérivées (`crates/nyx-core/src/git_watch.rs`, phase 2, Q-015). Sert de référence ADR pour l'adoption de la stack Git de v2.4, dans la discipline établie par PDR-0026 (une dépendance structurante = un PDR dédié nommant les crates).

## Context

v2.4 slice le moteur de diff Git (Q-015, PDR-0012 / PDR-0015) : la **review est une vue dérivée** du diff d'un `(workspace, repository)`, calculée à la demande, **jamais stockée** (PDR-0015 / PDR-0013). Ce moteur vit dans le **core shell-agnostique** pour que le **sidecar** (PDR-0007) le pilote et expose le résultat au renderer ET au MCP (PDR-0005), sans concern UI/temps-réel/commentaire (phases 2/3/4).

Il fallait donc une **plumbing Git** capable, en local pur (pas de remote — la review est 100 % locale), de : découvrir un dépôt, résoudre des rev-specs → SHA, lire des blobs, énumérer un diff tree→tree, produire des hunks ligne-à-ligne, et compter ahead/behind. Deux contraintes de discipline du repo pesaient sur le choix :

- **Pas de build C lourd.** Le reste de `nyx-core` évite déjà cmake/zlib-ng et privilégie le pur-Rust ou le vendoring maîtrisé (`libsqlite3-sys` `bundled`, `sysinfo` `default-features = false`, `portable-pty` sans cmake). Une dépendance Git ne devait pas réintroduire une toolchain C.
- **Cohérence prouvable.** Le renderer et l'agent MCP consomment le MÊME état ; le résultat du diff doit être identique quel que soit le backend qui l'a servi, et cette égalité doit être **testable**.

`gix` (plumbing Git pur-Rust) répond aux deux : pas de libgit2/C, et une API blob-diff (imara-diff) qui se normalise sur la même forme que la sortie `git diff`.

## Decision

- **Adopter `gix` comme backend PRIMAIRE** du moteur de diff et des vues dérivées, avec un **fallback `git` CLI cohérent** (`crate::proc_util::command`, durci contre le flash de console Windows). Tout diff est d'abord tenté par gix ; sur un échec d'ouverture/résolution, la MÊME opération repasse par le CLI. Les deux backends se normalisent sur la MÊME forme `RepoDiff`, et chaque résultat enregistre quel `DiffBackend` (`Gix` / `GitCli`) l'a produit, pour qu'un appelant — et les **tests de cohérence** — puissent asserter que gix et le CLI concordent (`crates/nyx-core/src/git_diff.rs`, doc de module + `diff_repo_with_mode`).
  - Côté gix : **découverte du dépôt** (`gix::open`), **résolution rev-specs → SHA** (`rev_parse_single`), **lecture de blobs** et **énumération tree→tree** (`diff_tree_to_tree`), **hunks** via `gix::diff::blob::UnifiedDiff` (imara-diff, algorithme Histogram), et **ahead/behind** via un revwalk qui masque l'ancêtrage du côté opposé (`rev_walk(...).with_hidden(...)`, dans `git_views.rs`).
  - **L'énumération index/worktree** (staged / unstaged / untracked) ne passe PAS par gix : l'index n'est pas un objet arbre, donc l'énumération du **jeu de fichiers** est déléguée au **porcelain `git -z` partagé** (`git diff --cached --name-status -z`, `git diff --name-status -z`, `git ls-files --others --exclude-standard -z`, `git status --porcelain -z`), tandis que les blobs/hunks restent lus par gix. Ce porcelain partagé est ce qui rend la **cohérence gix↔CLI prouvable par tests** : les deux backends partent du même jeu de changements.
- **Features gix retenues** (`default-features = false`, cf. `crates/nyx-core/Cargo.toml`) :
  - `sha1` — **OBLIGATOIRE**. C'est le backend de hash (`gix-hash`). Sans une feature de hash, l'enum `Kind` de `gix-hash` est vide et **`gix-hash` ne compile pas** ; le `default` de gix la tire implicitement, donc couper `default-features` impose de la réactiver explicitement. **Pur-Rust** (pas de dépendance C).
  - `blob-diff` — diff de blob ligne-à-ligne (les hunks), cœur du moteur.
  - `revision` — parsing de rev-spec + revwalk (commit / range, ahead/behind).
  - `dirwalk` — walk des fichiers non suivis (le côté `??` du diff working-tree).
  - `status` — statut index-vs-worktree / index-vs-HEAD (staged / unstaged).
  - `max-performance-safe` — l'accélération zlib-rs + prodash que gix embarque par défaut, **sans** la dépendance C zlib-ng (**pur-Rust, pas de cmake**).
  On écarte volontairement la stack réseau/transport (pas de remote, review 100 % locale) : `default-features = false` garde la surface serrée.
- **Multi-repo sans mélange d'identités Git.** Le moteur est clé sur UN dépôt à la fois par son **chemin absolu** (le chemin d'appartenance par-workspace, `crate::repository::member_absolute_path`). Chaque `RepoDiff` porte le `git_dir` résolu du dépôt, ses SHA `base`/`target` et les blob ids **par côté** — de sorte que le renderer agrégateur peut poser plusieurs reviews (une par `(workspace, repository)`) côte à côte SANS jamais mélanger les objets/refs d'un dépôt avec ceux d'un autre. Aucun état cross-repo ne vit ici.
- **Review = vue dérivée non stockée** (PDR-0015) : deux modes `Living` / `Pinned` (le mode est une propriété de la requête ; une review pinnée enregistre les SHA résolus pour se re-dériver à l'identique). Rien n'est persisté (PDR-0013).
- **Version épinglée en exact** `0.85.0` (`Cargo.toml` cohérent avec `Cargo.lock`, pas de drift), dans l'esprit de PDR-0026 pour une couche 0.x à API encore mouvante — un rebump délibéré après re-validation, pas via un range flottant.

### Rafraîchissement temps réel des vues dérivées : `notify` (watch fs OS-native, sans polling)

Le moteur ci-dessus calcule un `RepoGitView` **à la demande** ; pour que le renderer ET l'agent MCP voient une vue toujours à jour (Q-015, phase 2), il faut un **déclencheur** qui dit *quand* recalculer. La stack Git v2.4 adopte pour cela la dépendance **`notify = "7"`** (default features), consignée ici comme composant temps réel de la même stack (et non dans un PDR séparé, cette source d'événements étant nettement plus légère et périphérique que `gix` — une seule source d'événements, pas un moteur à backends multiples).

- **Rôle : source de changement filesystem OS-native.** `notify` s'appuie sur le mécanisme de watch du noyau — **inotify** sur Linux, **FSEvents** sur macOS, **ReadDirectoryChangesW** sur Windows — pour signaler qu'un fichier du work-tree a été édité ou qu'un chemin `.git` porteur d'état a changé. Utilisé uniquement par `crate::git_watch` (`crates/nyx-core/src/git_watch.rs`) ; le shell (sidecar) le pilote et pousse le résultat sur le pipe EventSink v2.1.
- **Justification no-polling.** Le kernel **notifie** un changement au lieu qu'on interroge le disque en boucle : le watcher **sonne** sur l'événement et on recalcule + pousse à ce moment-là, plutôt que de re-lire périodiquement l'arbre de chaque repo (coûteux, latent, et qui bat inutilement le disque au repos). C'est la garantie « sans polling » du rafraîchissement temps réel.
- **Debounce + allowlist `.git` porteuse d'état.** Un `git checkout` / `git commit` touche des centaines de chemins ; chaque événement brut ne fait qu'**armer** un timer de debounce par repo (`DEBOUNCE`, `git_watch.rs`), coalescant la rafale en **un seul** recompute + push. Côté `.git`, seuls les chemins réellement porteurs d'état arment le debounce (`is_state_bearing_git_path` : `HEAD`, `refs/…`, `logs/…`, `index`), ce qui filtre le bruit des écritures d'objets. Les backends OS de `notify` sont **event-driven** ; le fallback poll interne n'est pas utilisé.
- **Default features assumées.** On garde les features par défaut de `notify` (pas de `default-features = false`) : c'est ce qui active le backend **FSEvents** sur macOS ; sur Linux/Windows ces features par défaut sont inertes. La surface reste minimale (crate mature 1.0+, `notify = "7"` en range majeur cohérent avec `serde = "1"` / `regex = "1"`, pas une couche 0.x à épingler en exact comme `gix`).
- **Renvoi Cargo.toml.** La justification par-feature et le rôle exact sont commentés inline dans `crates/nyx-core/Cargo.toml` (bloc `notify = "7"`) ; ce PDR en est la trace ADR (indexée `C-055`).

## Alternatives écartées

- **`git2` / libgit2** (binding C de libgit2) : rejeté. Réintroduit une **toolchain C** et un build lourd (le contraire de la discipline `nyx-core` : pas de cmake, pur-Rust ou vendoring maîtrisé). gix offre la même plumbing en pur-Rust.
- **git CLI seul** (tout par sous-processus, parsing de sortie) : rejeté comme backend primaire. Le parsing de la sortie textuelle est **fragile** (préfixes mnémoniques `i/`/`w/`/`c/`, marqueurs binaires, `\ No newline`), impose une **dépendance runtime** à un `git` installé, et un sous-processus par diff est coûteux. Le CLI reste néanmoins comme **fallback** (et comme autorité du porcelain d'énumération index/worktree, que gix ne sait pas exprimer en diff d'arbre) — c'est ce qui garde le moteur toujours cohérent quand gix ne sait pas ouvrir/résoudre.
- **Tout-gix sans fallback** : rejeté. Les surfaces **index/worktree** (staged/unstaged/untracked) sont ambiguës à exprimer via gix (l'index n'est pas un arbre) et certaines dispositions/limitations gix ne résolvent pas ; sans fallback CLI, ces cas casseraient au lieu de dégrader proprement. Le duo gix-primaire + CLI-fallback + porcelain partagé donne à la fois pureté Rust ET couverture complète des surfaces.
- **Polling / re-read périodique pour le temps réel** (au lieu de `notify`) : rejeté. Interroger le disque en boucle (stat/re-read de chaque repo watché) est coûteux, latent (la fraîcheur est bornée par l'intervalle de poll), et bat le disque au repos alors que rien ne change. `notify` inverse le sens : le kernel **pousse** l'événement (inotify/FSEvents/RDCW), on ne recalcule que sur changement réel — même invariant de fraîcheur, sans le coût de fond.

## Consequences

- Nouvelle dépendance `gix = { version = "0.85.0", default-features = false, features = ["sha1", "blob-diff", "revision", "dirwalk", "status", "max-performance-safe"] }` dans `crates/nyx-core/Cargo.toml`, répercutée dans `Cargo.lock`. Chaque feature est justifiée en commentaire dans le `Cargo.toml`, ce PDR en est la trace ADR.
- Le moteur de diff (`git_diff.rs`) et les vues dérivées (`git_views.rs`) sont la **base** du viewer de diff virtualisé (phase 3) et du rafraîchissement temps réel des vues dérivées (phase 2) : le shape `RepoDiff` / `RepoGitView` (sérialisable serde, stable) est le contrat que le renderer et le MCP consomment.
- La **cohérence gix↔CLI** est un invariant testé (le `DiffBackend` enregistré + le porcelain partagé permettent de comparer les deux chemins) ; c'est la contrepartie assumée de garder deux backends.
- Pas de toolchain C ajoutée (pas de zlib-ng, pas de cmake) : le build de `nyx-core` reste pur-Rust côté Git, cohérent avec `libsqlite3-sys` bundled et `sysinfo`/`portable-pty`.
- Nouvelle dépendance `notify = "7"` (default features) dans `crates/nyx-core/Cargo.toml`, répercutée dans `Cargo.lock` : la **source d'événements filesystem** du rafraîchissement temps réel (`crate::git_watch`, phase 2). C'est ce qui rend le `RepoGitView` toujours frais pour le renderer ET le MCP **sans polling** ; le rôle par-OS et la justification no-polling sont commentés inline dans `Cargo.toml`, ce PDR (§ *Rafraîchissement temps réel des vues dérivées*) en est la trace ADR, indexée `C-055` dans `docs/product/README.md`.
