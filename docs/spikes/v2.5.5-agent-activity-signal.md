# Spike — détection fiable de l'activité réelle d'un agent (idle vs actif)

- **PRD** : v2.5.5 sessions agent (`01KX8Z4E7B3PYW2DGCTTKXCHYC`), phase 4.
- **Task** : `01KX8Z6SJAGN479Y0Q344PWKJD` (support / investigation).
- **Question (crux)** : sait-on distinguer de façon FIABLE « process vivant mais idle en
  attente d'input » de « Claude génère activement » ? C'est le pré-requis de l'unload : on ne
  décharge JAMAIS une session active.
- **Verdict** : **OUI — crux validé.** Le signal fiable est **`agent_activity`** (l'état
  runtime Working/Waiting/Idle), avec l'**inactivité I/O du PTY** comme *seuil* de
  temporisation. Seuil recommandé : **15 min d'inactivité**.

---

## 1. Signaux évalués

Trois signaux étaient candidats (cf. spec de la task). Bilan de fiabilité :

### 1a. `agent_activity` (Working / Waiting / Idle) — **LE discriminateur** ✅

`crates/nyx-core/src/agent_activity.rs`. Machine à états runtime, en mémoire, alimentée par
les hooks per-turn du plugin Claude (`UserPromptSubmit`, `PreToolUse`/`PostToolUse`,
`SubagentStart`/`SubagentStop`, `Notification`, `Stop`/`StopFailure`). Clé de map = le
**terminal RECORD id** (`NYX_TERMINAL_ID`) — exactement la même clé que les resume parks
(`resume_parks.rs`) et que le snapshot lu par le renderer (`agent_activity_snapshot`).

Pourquoi c'est LE bon signal :

- **Il mesure directement ce qui nous intéresse** : `Working` = Claude génère (entre
  `UserPromptSubmit` et `Stop`, ou tant qu'un outil/sous-agent est en vol) ; `Idle` = tour
  terminé, en attente d'un prompt ; `Waiting` = bloqué sur l'utilisateur.
- **0-stale sur les actions longues** (le point critique) : tant que `in_flight > 0` (un
  outil en cours) OU `subagents_in_flight > 0`, l'état reste `Working` — **sans aucun timer
  de péremption**. Un outil de 10 min qui n'émet rien reste `Working` : l'unload ne peut
  JAMAIS confondre une « action en cours » avec de l'idle. C'est l'invariant « exception :
  session avec action en cours » réalisé au niveau du signal.
- **Anti-phantom** : vide au boot (jamais persisté), et un `clear` sur mort PTY / SessionEnd
  / close ramène à Idle. Pas de `Working` fantôme qui bloquerait éternellement l'unload.
- **Fail-safe sur le seul trou documenté** : un `Esc` « nu » (interruption sans `Stop`)
  laisse l'état `Working` jusqu'au prochain prompt. Pour l'unload c'est la BONNE direction :
  on GARDE (jamais un faux « idle »), et ça s'auto-répare au prompt suivant.

### 1b. `busy` / `exec_state` (OSC 133 + foreground pgid) — **inutilisable seul** ❌

`crates/nyx-core/src/osc133.rs`, `crates/nyx-sidecar/src/runtime/pty.rs` (`terminal_info`,
`foreground_pgid`). Ce signal dit « une commande de premier plan tourne dans le shell ». Or
pour une session agent, **`claude` EST le process de premier plan pendant toute la durée de
la session** : le `foreground_pgid` pointe sur `claude` que Claude soit en train de générer
ou qu'il attende sagement à son prompt. Le bit « busy » est donc allumé dans les deux cas —
il ne sépare pas idle-au-prompt de génération. Le commentaire de `osc133.rs` l'acte
explicitement : « the OS busy signal — not OSC 133 — owns the running state ». **Rejeté**
comme discriminateur (il reste utile pour un shell *non-agent*, hors-scope ici).

### 1c. Inactivité I/O du PTY (pas d'output ni de frappe depuis N min) — **le seuil** ⏱️

`crates/nyx-sidecar/src/runtime/pty.rs` : tout l'output traverse le pump (`run_pump` →
`Event::TerminalOutput`) et toute frappe passe par `PtyManager::write`. On peut donc dater la
DERNIÈRE I/O (`last_io`) par terminal. Ce n'est **pas** un discriminateur idle/actif fiable
seul (Claude peut « réfléchir » ou lancer un long outil sans output pendant un moment, et un
build silencieux produit 0 output tout en étant actif). Mais c'est le **bon knob de seuil** :
posé PAR-DESSUS le gate `Idle`, il évite de décharger une session qu'on vient à peine de
quitter, et il couvre le cas « le terminal a bougé récemment » indépendamment des hooks.

---

## 2. Le signal retenu : combinaison `Idle` (gate) + inactivité I/O (seuil)

Décision d'unloader une session agent, pour un terminal `record_id` :

```
UNLOAD  ⇔  activity(record_id) == Idle          (gate de SÛRETÉ : jamais Working/Waiting)
        ∧  !visited(record_id)                   (pas le terminal actuellement regardé)
        ∧  idle_for(record_id) >= THRESHOLD      (inactivité I/O au-delà du seuil)
```

- **Gate de sûreté** = `agent_activity == Idle`. `Working` (génère OU action en vol) et
  `Waiting` (bloqué sur l'utilisateur) ⇒ **JAMAIS unloadé**. C'est l'invariant central.
- **Exception « action en cours »** : gratuite — une action en vol force `Working` (0-stale),
  donc déjà exclue par le gate.
- **Seuil** = inactivité I/O (`now - last_io`). **Recommandé : 15 min.** Assez long pour ne
  pas décharger une session juste mise de côté ; assez court pour libérer les ressources
  d'une session réellement dormante. Valeur exposée comme constante partagée
  (`RECOMMENDED_THRESHOLD_SECS = 900`) pour que politique et preuve s'accordent.
- **Réveil sur ouverture** : à la revisite, on réutilise le mécanisme lazy de la phase 2
  (park + inject `claude --resume <id>` au re-spawn du PTY) — aucun nouveau chemin de resume.

## 3. Preuve empirique

Test : `crates/nyx-core/tests/agent_activity_signal_spike.rs` (exerce la VRAIE machine
`AgentActivityStore`, i.e. le code exact que pilotent les hooks MCP en prod). 6 cas, tous
verts (`cargo test -p nyx-core --test agent_activity_signal_spike`) :

1. `agent_activity_separates_generating_from_idle` — `UserPromptSubmit` ⇒ `Working`,
   `Stop` ⇒ `Idle`. Le discriminateur de base.
2. `long_action_in_flight_never_reads_idle` — 1000 observations pendant qu'un outil est en
   vol : jamais `Idle` ; un sous-agent d'arrière-plan garde `Working` après le `Stop` ;
   `Idle` seulement quand la dernière action finit. **Prouve le 0-stale + l'exception
   action-en-cours.**
3. `blocked_on_user_reads_waiting_not_idle` — un prompt de permission ⇒ `Waiting` (≠ `Idle`) :
   une session bloquée sur l'utilisateur n'est pas déchargeable.
4. `bare_interrupt_fails_safe_stays_working` — `Esc` nu ⇒ reste `Working` (fail-safe : jamais
   de faux idle), auto-réparé au prompt suivant.
5. `clear_on_death_drops_to_idle` — mort PTY ⇒ retour à Idle (pas de `Working` fantôme).
6. `recommended_threshold_is_fifteen_minutes` — verrouille le seuil (900 s).

La validation empirique du VOLET SEUIL (inactivité I/O sur un vrai PTY : idle au-delà du
seuil ⇒ déchargé ; actif ⇒ jamais) est faite sur `sh` réel dans la slice d'unload
(`crates/nyx-sidecar/tests/agent_unload.rs`), qui pilote un vrai PTY à la façon de
`resume_inject.rs`.

---

## 4. Conclusion / faisabilité

**Crux VALIDÉ.** On sait détecter de façon fiable idle-vs-actif via `agent_activity`, avec un
seuil d'inactivité I/O de 15 min. Le signal est fail-safe (toute incertitude penche vers
« garder chargé », jamais « décharger à tort »), 0-stale sur les actions longues, et déjà
keyé par le record id — donc directement branchable sur l'unload (task
`01KX8Z6T1J2AC65DHHZTCQ26Z4`) et sur le resume lazy de la phase 2. Aucun blocage : la slice
d'unload peut procéder sur ce signal.
