# Spike — boucle `nyx_next` single-session (spawn natif → gate → branch → re-spawn)

- **PRD** : v2.8 Harnais — moteur d'orchestration behavior-tree single-session
  (`01KY4DQS06B939Z1CM8CPE7TW0`), phase 1.
- **Task** : `01KY71HYTSHJCFHGSWGEE1FWR8` — *Dérisquage runtime* (le juge de paix du PRD).
- **Crux** : peut-on, en **UNE session agent**, faire piloter par `nyx_next` la boucle cœur
  — `spawn(coder via sous-agent NATIF)` → `gate(typecheck)` →
  `branch(rouge = re-spawn / vert = avance)` → `re-spawn` — **sans aucun spawn de session
  externe** (`claude -p` proscrit, pricing), avec **détection fiable de la fin du sous-agent
  natif** et **extraction de son résultat (le diff)**, et de façon **cross-provider** ?
- **Verdict** : **OUI — crux validé, sur 2 providers réels.** La boucle déterministe est
  prouvée verte en process sur le VRAI nyx-core (gate sur PTY + machine d'activité réelle +
  diff git), et démontrée LIVE sur **Claude** (2 sous-agents NATIFS `Task`, avec un vrai
  re-spawn sur rouge) **et OpenCode** (effecteur, modèle *free*). Aucun `claude -p`.

---

## 1. La boucle prouvée

```
            ┌───────────────────────── nyx tient l'état + la blackboard ─────────────────────────┐
            │                                                                                     │
  nyx_next ─┤ spawn_subagent(coder) ──► [dispatcher lance le sous-agent NATIF, in-session]        │
            │        ▲                                    │                                        │
            │        │                                    ▼  (fin détectée + diff extrait)         │
            │        │                          nyx_next(run, last_result=diff)                    │
            │        │                                    │                                        │
            │        │                     gate_check(typecheck)  ◄── nyx a le PTY, l'exécute      │
            │        │                                    │           LUI-MÊME et bloque           │
            │   (rouge) └──────── selector/branch ────────┤                                        │
            │                                             │ (vert)                                 │
            │                                             ▼                                        │
            │                                     transition(→ avance)                             │
            └─────────────────────────────────────────────────────────────────────────────────────┘

  La session est un DISPATCHER MINCE : elle ne fait que `nyx_next` → exécuter l'action → `nyx_next`.
```

Propriétés voulues, toutes tenues :

- **Single-session** — le travail passe par les sous-agents NATIFS du provider (Claude
  `Task`) ; jamais de `claude -p`. Sur un provider sans sous-agents → dégrade en inline, la
  boucle se déroule quand même.
- **Enforcement dans le handler de verbe** — `gate_check` rouge ⇒ `nyx_next` ne renvoie
  **jamais** `Advance` ; il renvoie `Spawn` (re-spawn). La décision de branche est prise par
  le gate que **nyx** exécute, pas par un hook provider.
- **Détection-fin + extraction hook-free** — le signal de fin universel est **le rappel
  `nyx_next(last_result)` du dispatcher** (le retour de l'appel bloquant du sous-agent
  natif) ; `last_result` porte le diff. Aucun hook provider requis.

## 2. Les mécanismes de nyx-core exercés (le VRAI code)

### 2a. Le gate est exécuté par nyx, sur le PTY — `command::CommandPty`

`gate_check` = une managed command lancée par nyx sur le PTY, bloquante, dont **l'exit code
est la branche** (0 = vert, ≠ 0 = rouge). Le spike utilise le primitif synchrone exact que
le moteur utilisera : `CommandPty::spawn(cmdline, PtySize, cwd, env)` puis `wait() → Option<i32>`
(`crates/nyx-core/src/command.rs:395` / `:535`). Gate du spike : `node --check <file>` (un
parse/typecheck rapide et réel sur un fichier CommonJS). Voir
`crates/nyx-core/tests/nyx_next_loop_spike.rs:122` (`gate_is_green`).

> Note gate : `node --check` sur du CommonJS distingue fiablement valide (exit 0) d'erreur de
> syntaxe (exit 1). La détection-de-module ESM de Node 24 rend `--check` laxiste sur `export`
> — le sandbox est donc CommonJS. Le *mécanisme* prouvé (exit code d'une managed command =
> branche) est indépendant de l'outil ; les runs live plus bas montrent le même gate.

### 2b. La fin du sous-agent natif est détectée — universel + confort Claude

- **Universel (hook-free)** — le dispatcher rappelle `nyx_next(run, diff)` quand le sous-agent
  natif rend la main. Le retour de l'appel bloquant EST le signal de fin ; le diff EST le
  résultat. C'est ce qui rend la boucle cross-provider sans dépendre d'un hook.
- **Confort Claude** — en plus, nyx détecte la fin via sa VRAIE machine d'activité
  `agent_activity::AgentActivityStore` alimentée par les hooks `SubagentStart` / `SubagentStop`.
  Le spike exerce ce code réel : tant que le sous-agent natif est en vol la machine lit
  `Working` ; un `TurnFinished` arrivant pendant que le sous-agent est encore en vol **ne
  settle pas** (0-stale — nyx sait de façon fiable que le sous-agent n'a pas fini) ; seul le
  `SubagentFinished` fait passer à `Idle`. Idiome repris du spike v2.5.5
  (`tests/nyx_next_loop_spike.rs:360`–`:372`).

### 2c. Le résultat est extrait comme un diff git réel

`extract_diff` = `git -C <dir> diff` du working tree que le sous-agent a édité
(`crates/nyx-core/tests/nyx_next_loop_spike.rs:142`). C'est « l'extraction du résultat (diff) »
du critère.

### 2d. Le contexte de l'effecteur (hors-scope P1, tracé)

L'action `spawn_subagent(coder)` porte, en prod, des IDENTIFIANTS — `agent_id`, le `label` du
nœud, le `subject` quand il y en a un, le `mode` — et jamais le manuel : le sous-agent appelle
lui-même `agent_context(run_id, role, subject?)`
(`mcp_context::render_agent_context`) et tire son rôle et l'état du run. Le spike P1 ne construit
PAS ce câblage (effecteurs customisables = phase 5) ; il prouve la BOUCLE.

## 3. Preuve déterministe (en process, verte, reproductible)

Test : `crates/nyx-core/tests/nyx_next_loop_spike.rs`. Un interpréteur minimal (la state
machine de la boucle P1 — le vrai interpréteur de nœuds est phase 2) piloté via un `next()`
qui EST le handler `nyx_next`. Le gate est run par `CommandPty`, la fin de sous-agent par
`AgentActivityStore`, le résultat par `git diff`. Le seam `SubagentSpawner` modélise le
provider : `NativeTaskSpawner` (Claude `Task`, émet les hooks d'activité) vs
`InlineFallbackSpawner` (provider sans sous-agents, aucun hook).

```
cargo test -p nyx-core --test nyx_next_loop_spike
    running 3 tests
    test a_red_gate_makes_nyx_next_respawn_and_never_advance ... ok
    test nyx_next_drives_native_spawn_gate_branch_respawn_in_one_session ... ok
    test same_loop_holds_on_a_provider_without_native_subagents ... ok
    test result: ok. 3 passed; 0 failed
```

1. **`nyx_next_drives_native_spawn_gate_branch_respawn_in_one_session`** (`:401`) — la boucle
   complète via `Task` natif : attempt 0 sous-fixe (gate rouge → **RE-SPAWN**), attempt 1
   fixe (gate vert → **ADVANCE**). Trace exacte `Spawn(0) → Spawn(1) → Advance`, deux
   sous-agents dans UNE session, jamais d'`Advance` sur rouge (`:437`) ; fin de sous-agent
   natif détectée par la vraie machine (`Working` en vol, `Idle` à la fin, `:372`/`:454`) ;
   diff extrait porte le fix vert.
2. **`same_loop_holds_on_a_provider_without_native_subagents`** (`:466`) — MÊME boucle, MÊME
   trace, avec un provider **sans** sous-agents natifs ni hooks (inline fallback). La machine
   d'activité reste vide, et pourtant la boucle atteint le vert : *« un provider sans ces
   hooks perd juste le confort, pas l'enforcement »*. C'est l'axe multi-provider au niveau du
   MÉCANISME (la boucle est hook-free).
3. **`a_red_gate_makes_nyx_next_respawn_and_never_advance`** (`:511`) — l'invariant
   d'enforcement isolé : à un gate que nyx exécute et trouve rouge, `nyx_next` renvoie
   `Spawn` (re-spawn), jamais `Advance` ; seul le vert avance.

## 4. Preuve LIVE — axe 1 : Claude (sous-agents NATIFS `Task`)

Réalisée dans CETTE session (le dispatcher), en pilotant de vrais sous-agents natifs via le
**Task tool** (bloquant, in-session, sous abonnement — **zéro `claude -p`**). Sandbox git
`/tmp/nyx-v2.8-live-demo` avec 2 erreurs de syntaxe (`add` et `sub`).

**Gate initial (rouge)** — `node --check impl.js` → `SyntaxError: Unexpected token ';'`, exit 1.

**Itération 1** — `nyx_next` → `Spawn(coder)`. Sous-agent NATIF #1 (scopé à `add`) lancé
(appel bloquant). **Fin détectée** = l'appel rend la main (rapport : `return a + b;`).
**Résultat extrait** = `git diff` :

```
-  return a + ;
+  return a + b;
```

**Gate** (nyx exécute `node --check`) → exit 1 (rouge, `sub` casse encore) → **branch rouge →
RE-SPAWN**.

**Itération 2** — `nyx_next` → `Spawn(coder)` (avec le feedback du gate). Sous-agent NATIF #2
(scopé à `sub`) lancé. **Fin détectée** au retour ; **diff extrait** :

```
-  return a + ;        -  return a - ;
+  return a + b;       +  return a - b;
```

**Gate** → exit 0 (**vert**) → **branch vert → ADVANCE** (transition).

> Le scoping de chaque sous-agent (l'un `add`, l'autre `sub`) est délibéré : il force un vrai
> re-spawn avec DEUX sous-agents natifs distincts, chacun faisant une unité de travail —
> exactement la branche rouge → re-spawn du critère, prouvée avec du vrai code de sous-agent.

Deux sous-agents natifs, une seule session, une vraie boucle rouge→re-spawn→vert→avance.

## 5. Preuve LIVE — axe 2 : OpenCode (2e provider réel)

`opencode` est installé et fonctionnel, avec des modèles **gratuits** (`opencode/*-free`) —
donc démontrable sans coût ni `claude -p`. Sandbox git `/tmp/nyx-v2.8-live-opencode`, 1 erreur
de syntaxe. Effecteur lancé :

```
opencode run --agent build -m opencode/north-mini-code-free "…fix the syntax error in impl.js…"
    → build · north-mini-code-free
    → Read impl.js
    ← Edit impl.js   (-  return a + ;  /  +  return a + b;)
    "Fixed. The add function now correctly returns a + b in impl.js:2."
    EXIT: 0
```

- **Fin détectée (hook-free)** — le process `opencode run` **sort** (exit 0) : c'est le signal
  de fin, sans aucun hook. OpenCode expose aussi `run --format json` (flux d'events structuré
  se terminant par un event terminal) comme signal de fin explicite.
- **Résultat extrait** — `git diff` du sandbox → `-return a + ; / +return a + b;`.
- **Gate** — nyx exécute `node --check impl.js` → exit 0 (**vert**) → **ADVANCE**.

Les DEUX capacités crux (détection-fin + extraction-résultat, hook-free) tiennent donc sur un
2e provider réel, et le gate/branch reste piloté par nyx. L'axe Claude reste la preuve
*pleine* du sous-agent natif in-session ; l'axe OpenCode prouve les capacités crux + fournit
la facilité native documentée ci-dessous pour la version in-session complète.

### Table détection-fin / extraction par provider

| Provider | Sous-agent natif | Détection de fin (hook-free) | Extraction résultat |
|---|---|---|---|
| **Claude** | `Task` tool (in-session, abonnement) | retour de l'appel `Task` bloquant ; **+ confort** `AgentActivityStore` (`SubagentStart`/`Stop`) | diff git du working tree |
| **OpenCode** | `opencode agent` / `@agent`, ACP server, `run --agent` | exit du process + event terminal de `run --format json` | diff git du working tree |
| **Codex** | subagents / `codex exec` + `apply_patch` | exit du process / dernier event | diff git du working tree |

### Statut d'installation des providers (env de ce spike)

- **Claude** — OK, prouvé LIVE (§4).
- **OpenCode** — OK, prouvé LIVE (§5), modèles *free* disponibles.
- **Codex** — **installé mais wrapper cassé** : `/home/kris/.local/bin/codex` dépend de
  `mise`/`npx` non résolus (`Could not resolve npm bin for @openai/codex`) → non lançable en
  l'état. Non-bloquant : le critère demande « Codex **OU** OpenCode », et OpenCode couvre
  l'axe 2. Mécanisme Codex documenté ci-dessus ; pour le lancer réellement il faut réparer le
  wrapper (`mise` + `npx` sur le PATH).

## 6. Conclusion / faisabilité

**Crux VALIDÉ.** La boucle single-session `nyx_next` — `spawn(natif)` → `gate` (exécuté par
nyx sur le PTY) → `branch` → `re-spawn` — est prouvée déterministe en process (3 tests verts
sur le vrai nyx-core) et démontrée LIVE sur 2 providers réels (Claude, sous-agents natifs
`Task` avec re-spawn ; OpenCode, effecteur *free*), **sans aucun `claude -p`**. La fin du
sous-agent est détectée de façon fiable et hook-free (rappel du dispatcher + confort
`AgentActivityStore` sur Claude), et son résultat est extrait comme un diff git. L'enforcement
(gate rouge ⇒ jamais `Advance`) vit dans le handler du verbe, pas dans un hook → il tient à
l'identique sur un provider sans sous-agents.

Aucun blocage runtime pour la suite. Ce que les phases suivantes construisent (hors-scope
P1) : le schéma DB `workflows`/`nodes`/`workflow_runs` (P2), l'interpréteur de nœuds général
composites+feuilles (P2), le vrai verbe `nyx_next` MCP (P3), l'enforcement dans les handlers
de verbes existants (P3), `spawn_subagent` multi-provider productisé (P3), l'authoring MCP +
seeds (P4), les effecteurs customisables (P5), l'UI React Flow (P6), le gate e2e (P7).
